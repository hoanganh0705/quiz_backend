# PHASE 10 — REVISED SEED AUDIT

## Objective

Determine the **minimum business seed data** required to make every API endpoint testable through normal application workflows (Postman / integration testing). This is NOT a list of "all tables that should be populated" — it is a classified inventory of what is strictly required, what is helpful, and what should not be seeded at all because it is generated by the API itself.

## Classification rules

Every missing table was scored against these questions:

- **A.** Can this table be populated naturally by calling existing APIs? (YES / NO)
- **B.** If YES — which endpoint(s) create it?
- **C.** If NO — why can't it be created naturally? Which API requires the data before testing?
- **D.** Would seeding make API testing easier but is not strictly required?

Outcomes:

| Symbol | Meaning |
| --- | --- |
| ✅ REQUIRED SEED | Pre-existing rows are mandatory for at least one endpoint to be exercised. Without them, an endpoint returns 404 / "not found" and cannot be tested through normal API use. |
| ⚠ OPTIONAL SEED | Rows can be created through normal API calls; seeding them just shortens the test setup. Useful for list / detail endpoints but not required. |
| ❌ DO NOT SEED | The data is runtime-generated. Either it is created as a side-effect of an earlier API call, or it is internal bookkeeping that the application owns. Seeding it would mask real flow bugs. |

## Minimal Required Seed Set (Postman-only tester)

To run every API endpoint via Postman without ever touching the seed script beyond `users + categories + tags + badges + quizzes + versions + questions + answer_options + user_profiles (optional)` and seeding an admin role on one user, the **bare minimum** is:

1. `users` (with at least one verified account per role: admin, moderator, regular user)
2. `categories` (a handful, so category-driven listings work)
3. `tags` (a handful, so tag-driven listings work)
4. `badges` (the badge catalog so the achievements endpoints have data)
5. `quizzes` + `quiz_versions` + `quiz_questions` + `quiz_answer_options` (so quiz detail / stats / attempt endpoints have content)
6. `user_ranking` (one row per seed user, so `GET /users/me/ranking` and `/leaderboard/me` return data — otherwise they return null gracefully but cannot be fully tested)

Everything else is either:

- **Runtime-generated** by the API itself (sessions, tokens, attempts, votes, follows, etc.), or
- **Optional** for richer Postman walkthroughs (tournaments, instance scenarios, reviews, notifications, bookmarks, discussions, user_badges, ranking snapshots).

## Recommended Seed Order

If a tester wants the smallest possible seed script that allows every endpoint to be exercised in a single Postman walkthrough:

1. `users` (admin, moderator, 2 regular users)
2. `badges` + `badge_rules` (catalog)
3. `categories` + `tags` (taxonomy)
4. `quizzes` + `quiz_versions` + `quiz_questions` + `quiz_answer_options` (content)
5. `user_ranking` (one row per user so ranking endpoints return non-null)

Everything else the tester creates via the API as they go:

- `POST /auth/login` → `user_sessions`
- `POST /quizzes/:id/attempts` → `quiz_attempts` + `quiz_attempt_answers`
- `POST /categories/:id/follow` → `category_follows`
- `POST /social/follow/:userId` → `user_follows`
- `POST /social/friend-request/:userId` → `friendships`
- `POST /instances/:id/join` → `quiz_instance_players`
- `POST /discussions/threads` + comments + votes → `discussion_*` rows
- `POST /bookmarks/collections` + quizzes → `bookmark_*` rows
- `POST /tournaments` + rounds + register → `tournament_*` rows
- `PATCH /users/me` → `user_profiles`
- `PATCH /notifications/preferences` → `notification_preferences`

Optional seeds (tournaments in various statuses, sample notifications, sample reviews, sample discussions, sample bookmarks, sample user_badges, sample ranking history) can be added at the tester's discretion to skip the "first create it" step, but none of them are required.
