# PHASE 10 — SCHEMA-GROUNDED SEED AUDIT

## Objective

Determine the **minimum business seed data** required to make every API endpoint testable through normal application workflows (Postman / integration testing). This document is **schema-grounded**: every classification is cross-checked against the actual `pgTable` definitions under `src/core/database/schema/`, and the seed behaviour is cross-checked against the actual files under `src/commands/seed/`.

The classification is **not** a list of "all tables that should be populated" — it is an inventory of what is strictly required, what is helpful, and what must not be seeded because it is generated by the API itself.

## Classification Rules

Every table was scored against these questions:

- **A.** Can this table be populated naturally by calling existing APIs? (YES / NO)
- **B.** If YES — which endpoint(s) create it?
- **C.** If NO — why can't it be created naturally? Which API requires the data before testing?
- **D.** Would seeding make API testing easier but is not strictly required?

Outcomes:

| Symbol | Meaning |
| --- | --- |
| ✅ REQUIRED SEED | Pre-existing rows are mandatory for at least one endpoint to be exercised. Without them, an endpoint returns 404 / "not found" and cannot be tested through normal API use. |
| ⚠ OPTIONAL SEED | Rows can be created through normal API calls; seeding them just shortens the test setup. Useful for list / detail endpoints but not required. |
| ❌ DO NOT SEED | The data is runtime-generated. Either it is created as a side-effect of an earlier API call, or it is internal bookkeeping that the application owns. Seeding it would mask real flow bugs. |

## Minimal Required Seed Set (Postman-only tester)

To exercise every API endpoint via Postman without re-running the seed script beyond the foundation tier, the **bare minimum** is:

1. `users` (with at least one verified account per role: admin, moderator, regular user)
2. `categories` (a handful, so category-driven listings work)
3. `tags` (a handful, so tag-driven listings work)
4. `badges` + `badge_rules` (the badge catalog + rule configuration so the achievements pipeline can evaluate)
5. `quizzes` + `quiz_versions` + `quiz_questions` + `quiz_answer_options` (so quiz detail / stats / attempt endpoints have content)
6. `user_ranking` (one row per seed user, so `GET /users/me/ranking` and `/leaderboard/me` return data — otherwise they return null gracefully but cannot be fully tested)

Everything else is either:

- **Runtime-generated** by the API itself (sessions, tokens, attempts, votes, follows, etc.), or
- **Optional** for richer Postman walkthroughs (tournaments, instance scenarios, reviews, notifications, bookmarks, discussions, user_badges, ranking snapshots).

## Documented Deviations From The Strict Classification

A small number of "❌ DO NOT SEED" tables are seeded in practice. These are deliberate, well-scoped exceptions — not an oversight. They are called out here so reviewers do not flag them as audit violations.

| Table | Strict classification | Actual seed behaviour | Justification |
| --- | --- | --- | --- |
| `quiz_categories` (join) | ❌ DO NOT SEED | Seeded directly by `quiz.seed.ts → ensureTaxonomy()` for every quiz that has a `categorySlug`. | The quiz-creation API accepts categories inline, but seeding them in the same transaction as `quizzes` keeps the seed script atomic and lets category-driven filters (`GET /quizzes?categoryId=...`, `GET /categories/:slug/quizzes`) return non-empty results immediately. No application flow is bypassed: the rows are identical to what `POST /quizzes` would have produced. |
| `quiz_tags` (join) | ❌ DO NOT SEED | Seeded directly by `quiz.seed.ts → ensureTaxonomy()` for every quiz that has `tagSlugs`. | Same rationale as `quiz_categories`. The tag-driven filters (`GET /tags/:slug/quizzes`, `GET /quizzes?tagId=...`) need rows to return results; seeding in the same transaction mirrors what the create-quiz endpoint does in one request. |

A `quiz_categories` / `quiz_tags` row can be deleted via the quiz-update API to verify the endpoints still work after a manual removal, but the seed ships with them populated so the smoke-test walkthrough is one-step.

## Recommended Seed Order

If a tester wants the smallest possible seed script that allows every endpoint to be exercised in a single Postman walkthrough, the order is the same order `runFoundation()` + `runDevelopment()` execute in `src/commands/seed/index.ts`:

1. `badges` + `badge_rules` (catalog — no FK deps)
2. `users` (with role diversity)
3. `categories` + `tags` (taxonomy)
4. `quizzes` + `quiz_versions` + `quiz_questions` + `quiz_answer_options` + `quiz_categories` + `quiz_tags` (content + taxonomy joins)
5. `user_ranking` (+ `rank_history` + `ranking_milestones` for the active users)
6. `user_badges` (referencing badge slugs and usernames)
7. `notifications` + `notification_preferences`
8. `quiz_reviews` (referencing quiz slugs and usernames)
9. `discussion_threads` + `discussion_comments` + `discussion_votes`
10. `bookmark_collections` + `bookmarked_quizzes`
11. `tournaments` + `tournament_rounds` + `tournament_participants` (scenarios)
12. `quiz_instances` (scenarios)

Everything else the tester creates via the API as they go:

- `POST /auth/login` → `user_sessions`
- `POST /attempts/start` + `POST /attempts/:id/answers` → `quiz_attempts` + `quiz_attempt_answers` + `quiz_attempt_events` + `quiz_stats`
- `PATCH /users/me` → `user_profiles`
- `PATCH /notifications/preferences` → (idempotent update of the seeded row)
- `POST /categories/:id/follow` → `category_follows`
- `POST /tags/:id/follow` → `tag_follows`
- `POST /social/follow/:userId` → `user_follows`
- `POST /social/friend-request/:userId` → `friendships`
- `POST /social/block/:userId` → `blocked_users`
- `POST /instances/:id/join` → `quiz_instance_players`
- `POST /discussions/threads` + comments + votes + reports → `discussion_*` rows
- `POST /bookmarks/collections` + quizzes → `bookmark_*` rows
- `POST /tournaments` + rounds + register + start round attempt → `tournament_*` rows

Optional seeds (tournaments in various statuses, sample notifications, sample reviews, sample discussions, sample bookmarks, sample user_badges, sample ranking history) can be added at the tester's discretion to skip the "first create it" step, but none of them are required.
