## 1. Executive Summary

### Overall Contract Health Score: **5 / 10**

The `instance` module implements the documented lifecycle (open → running → closed) and the controller/service/presenter layering is consistent with the rest of the project, but it has several **critical implementation bugs** that return 500 on documented behavior (invalid status/difficulty filters, missing `quizVersionId`, broken leaderboard cursor), **wire-shape mismatches** (Postgres timestamp strings on the list endpoint instead of ISO 8601, `rank` returned as a string instead of a number, duplicate-join returns the wrong error code), and **systemic documentation gaps** (missing `format: 'uuid'` on every `:id` path parameter, generic `ErrorResponseExamples` for module-specific errors, missing module-level OpenAPI regression test).

## 2. Module Overview

The `instance` module owns the real-time multiplayer quiz session lifecycle (rooms, host control, player join/exit, live leaderboard, WebSocket-based real-time event push). It coordinates with the Attempt module to attach individual attempt results to instance players.

| Resource | Description |
|---|---|
| `QuizInstance` | A real-time room: `quizVersionId`, `hostUserId`, `status ∈ {open, running, closed, finished}`, `maxPlayers`, `startedAt`, `closedAt`. |
| `InstancePlayer` | A participant: `userId`, `status ∈ {joined, ready, playing, disconnected, finished}`, `score`, `rank`, `attemptId`. |

**Lifecycle:** `open → running → closed` (with `finished` as a terminal DB enum value the runtime does not produce).

**Permissions:** No `@Permissions` guards. Every REST endpoint requires a valid JWT. WebSocket connections are authenticated via handshake token — WebSocket is out of scope for this REST contract audit.

### 4.1 `POST /api/v1/instances`

| Aspect | Detail |
|---|---|
| Controller | `InstanceController.createInstance` (`instance.controller.ts:131-159`) |
| Application | `InstanceApplicationService.createInstanceForController` (`instance.application.service.ts:112-122`) |
| Domain | `InstanceService.createInstance` (`instance.service.ts:49-81`) |
| Repository | `QuizInstanceRepository.createInstanceWithHost` (`quiz-instance.repository.ts:74-135`) |
| Request DTO | `CreateInstanceDto { quizVersionId: uuid (req), maxPlayers?: int[2..100] }` |
| Response DTO | `CreateInstanceResponseDto { instanceId, message }` wrapped in `WrappedDto` |
| Status | `201 Created` |

#### Critical findings

**1.1 — Non-existent `quizVersionId` returns 500 with raw SQL in `detail`**
- **Current behavior**: `POST /instances` with `quizVersionId="00000000-…"` returns `500 GLOBAL_INTERNAL_ERROR` with the full Postgres FK violation text (`"insert or update on table \"quiz_instances\" violates foreign key constraint \"quiz_instances_quiz_version_id_fkey\""`) in `detail`.
- **Documented behavior**: Spec lists only `201/400/401`. A 400 is expected (validation problem), never a 500.
- **Root cause**: `quiz-instance.repository.ts:74-135` inserts blindly. The Postgres error code `23503` bubbles up to the global filter which exposes the raw SQL. No pre-validation, no exception translation.
- **Implementation correct?** No.
- **Documentation correct?** Yes.
- **Recommendation**: Translate `23503` to a 400 (or 404 with a new `QUIZ_VERSION_NOT_FOUND` code). Pre-check via `quizVersionRepo.exists(...)` if cheap, or wrap the Drizzle error in the service layer. **Never** leak SQL text in `detail`. **Breaking API contract** (status code change for this specific input). Requires a product decision (400 vs. 404).
- **Suggested fix sketch** (illustrative — to be discussed in the implementing PR):

  ```ts
  // src/modules/quiz/domain/errors/quiz-domain.errors.ts
  export class QuizVersionNotFoundError extends QuizDomainError {
    readonly code = 'QUIZ_VERSION_NOT_FOUND';
    constructor(message = QUIZ_VERSION_NOT_FOUND_MESSAGE) { super(message); }
  }

  // src/modules/instance/domain/instance.service.ts
  try {
    const result = await this.instanceRepository.createInstanceWithHost({...});
    ...
  } catch (error) {
    if (isPostgresForeignKeyViolation(error)) {
      throw new QuizVersionNotFoundError('Quiz version not found');
    }
    throw error;
  }
  ```

#### Lower-severity findings

**1.2** *(Low)* — `maxPlayers` Swagger example says `default: null`; runtime falls back to `null` when omitted. ✓ Consistent.
**1.3** *(Low)* — `quizVersionId` is correctly declared with `format: 'uuid'` in the spec. ✓.
**1.4** *(Low)* — The 401 example in the shared `ErrorResponseExamples.unauthorized` says `detail = "Invalid or expired access token"`, but the actual runtime detail is `"Authorization header is missing"`. The discrepancy is global, not instance-specific, and lives in `src/common/swagger/swagger-schemas.ts:63-70`. **Documentation fix** in a separate PR.
**1.5** *(Info)* — The created instance auto-inserts the caller as a `joined` player via `createInstanceWithHost`. Consistent with the lifecycle doc. ✓.

### 4.2 `GET /api/v1/instances`

| Aspect | Detail |
|---|---|
| Controller | `InstanceController.listInstances` (`instance.controller.ts:165-187`) |
| Application | `InstanceApplicationService.listInstancesForController` (`instance.application.service.ts:156-173`) |
| Domain | `InstanceService.listInstances` (`instance.service.ts:254-302`) |
| Repository | `QuizInstanceRepository.listInstances` (`quiz-instance.repository.ts:518-588`) |
| Request DTO | `ListInstancesQueryDto { cursor?, limit?, status?, difficulty? }` |
| Response DTO | `InstanceListResponseDto` wrapped in `WrappedPaginatedDto` with `PaginationMetaDto { kind: 'cursor' }` |
| Status | `200 OK` |

#### Critical findings

**2.1 — Invalid `status` or `difficulty` returns 500 with raw Postgres enum-violation text**
- **Current behavior**: `?status=invalid` or `?difficulty=invalid` → `500 GLOBAL_INTERNAL_ERROR` with `invalid input value for enum quiz_instance_status: "invalid"` (or similar).
- **Documented behavior**: The OpenAPI doc advertises both as enums with `enum: ['open','running','closed','finished']` and `enum: ['easy','medium','hard']` respectively. A 400 is expected.
- **Root cause**: `dto/request/instance.dto.ts:96-107` declares `status` and `difficulty` with `@IsOptional()` only — no `@IsIn(…)` validator. The repository's `eq(quizInstances.status, params.filters.status as 'open' | 'running' | …)` casts the user input to a PG enum type without runtime validation. The PG enum rejection (`22P02`) becomes a 500.
- **Implementation correct?** No.
- **Documentation correct?** Yes.
- **Standard violation**: `docs/standards/validation.md:42` says "An enum field MUST declare `@IsEnum(EnumType)` and `@ApiProperty({ enum: EnumType })`."
- **Recommendation**: Add `@IsIn(INSTANCE_STATUSES)` and `@IsIn(QUIZ_DIFFICULTIES)` to the DTO. The same pattern is already used in `src/modules/quiz/dto/request/update-quiz-version.dto.ts:13` (`@IsIn(QUIZ_DIFFICULTIES)`). **Safe implementation fix** (matches documented behavior).

**2.2 — `createdAt` is emitted in Postgres format instead of ISO 8601**
- **Current behavior**: `data[*].createdAt = "2026-07-16 15:47:47.948+00"` (Postgres-formatted string).
- **Documented behavior**: DTO and OpenAPI schema declare `createdAt: string` with example `"2025-06-01T12:00:00.000Z"`. `docs/standards/api.md:80` says: "Every timestamp on the wire MUST be ISO 8601 UTC with milliseconds."
- **Root cause**: `transport/presenters/instance.presenter.ts:23-37` `wrapPaginatedDto` returns `data: [...payload.items]` **without** calling `normalizeTemporalFields`. `ApiResponse.ok` (used by all other instance endpoints) does normalize, but the paginated helper short-circuits it.
- **Implementation correct?** No.
- **Documentation correct?** Yes.
- **Recommendation**: Replace `data: [...payload.items]` with `data: normalizeTemporalFields([...payload.items]) as T[]` in `wrapPaginatedDto`. **Safe implementation fix**.

  ```ts
  // src/modules/instance/transport/presenters/instance.presenter.ts
  const wrapPaginatedDto = <T>(payload: {...}): ApiResponseEnvelope<T[]> => ({
    data: normalizeTemporalFields([...payload.items]) as T[],
    meta: { ... },
  });
  ```

#### High findings

**2.3 — Default `limit` behavior is documented but not explicitly stated in the DTO description**
- **Current behavior**: Omitting `limit` defaults to 20 (DTO default). `?cursor=…` without `limit` also defaults to 20.
- **Documented behavior**: `default: 20` is on the schema; the description says "Maximum number of instances to return per page" without mentioning the default.
- **Recommendation**: Add a one-line note to `@ApiPropertyOptional` for `limit`: `"Defaults to 20 when omitted."` **Safe documentation fix.**

**2.4 — Cursor decoding is permissive (no shape validation)**
- **Current behavior**: Any valid base64 JSON object decodes successfully; the repository silently ignores `cursor` keys that aren't `{ createdAt, instanceId }`.
- **Documented behavior**: Spec says "Decode base64 to JSON `{ createdAt, instanceId }`".
- **Root cause**: `instance.service.ts:270-274` does `JSON.parse(...) as InstanceCursorPayload` without checking fields.
- **Implementation correct?** No.
- **Documentation correct?** Yes.
- **Recommendation**: Validate the cursor's shape after parsing; on missing/wrong-typed fields, throw `BadRequestException('Invalid cursor')` (mirrors the leaderboard's `decodeBase64JsonCursor` behavior). **Safe implementation fix**.

**2.5 — Cursor `createdAt` is the raw Postgres string, not ISO 8601**
- **Current behavior**: `nextCursor` decodes to `{ createdAt: "2026-07-16 15:50:54.295+00", instanceId: "…" }`.
- **Documented behavior**: DTO description shows `"2026-06-25T10:30:00.000Z"`.
- **Root cause**: `instance.service.ts:296-300` does `JSON.stringify({ createdAt: lastItem.createdAt, ... })` directly, where `lastItem.createdAt` is the raw PG string.
- **Implementation correct?** No.
- **Documentation correct?** Yes.
- **Recommendation**: Normalize to `new Date(lastItem.createdAt).toISOString()` before encoding. **Breaking client SDK** (cursor payload shape changes); coordinate with frontend.

**2.6 — Same as 2.5 (envelope-leak)** — combined under 2.5.

**2.7 — N/A** (this endpoint has no path parameter).

**2.8 — Same root cause as 2.1** (covered under 2.1).

#### Lower findings

**2.9 *(Low)* — Cursor description on the DTO uses `base64` while the leaderboard DTO uses `base64url`**
- Both are decoded via the same `decodeBase64JsonCursor` helper (`base64url`).
- **Documentation fix** in a follow-up.

| Aspect | Detail |
|---|---|

#### Critical findings

**5.1 — Re-join (or self-join) returns `INSTANCE_FULL` instead of `PLAYER_ALREADY_JOINED`**
- **Current behavior**: A user (including the host) joining an instance they are already in gets `400 INSTANCE_FULL` ("Instance is full") even when the instance is far from full. The 500-reachable SQL behavior is fine; the user-facing code is wrong.

- **Implementation correct?** No.
- **Documentation correct?** Partly (`InstanceFullError` is documented; `PlayerAlreadyJoinedError` is not).
- **Recommendation**: Change `joinInstanceAtomic` to return a discriminator (`{ status: 'duplicate' | 'full' | 'joined' }`); throw `PlayerAlreadyJoinedError` (status `409`, code `PLAYER_ALREADY_JOINED` per `problem-code-mapping.ts:949-963`) for duplicates. **Breaking API contract** (status 400 → 409; `extensions.code` change). Requires coordinated frontend release.

**5.3 *(Medium)* — Host-self-join is a special case of 5.1** — same fix.

### 4.8 `GET /api/v1/instances/{id}/leaderboard`

| Aspect | Detail |
|---|---|
| Controller | `InstanceController.getLeaderboard` (`instance.controller.ts:328-359`) |
| Application | `InstanceApplicationService.getLeaderboardForController` (`instance.application.service.ts:184-211`) |
| Domain | `InstanceService.getLeaderboard` (`instance.service.ts:220-232`) |
| Repository | `QuizInstanceRepository.getLeaderboard` (`quiz-instance.repository.ts:380-459`) |
| Request DTO | `GetLeaderboardQueryDto { cursor?, limit? }` (cursor payload: `{ rank, instancePlayerId }`) |
| Response DTO | `InstanceLeaderboardResponseDto` wrapped in `WrappedPaginatedDto` with `PaginationMetaDto { kind: 'cursor' }` |
| Status | `200 OK` / `400` / `404 INSTANCE_NOT_FOUND` |

#### Critical findings

**8.1 — Cursor pagination crashes with 500 on the second page**
- **Current behavior**: `?cursor=eyJyYW5rIjoiMyIsImluc3RhbmNlUGxheWVySWQiOiIuLi4ifQ&limit=1` → `500 GLOBAL_INTERNAL_ERROR` with `column "row_rank" does not exist` in `detail`.
- **Documented behavior**: Spec says cursor pagination is supported.
- **Root cause**: `quiz-instance.repository.ts:393-398` uses `row_rank` (a `row_number() over (...)` window function) inside a `WHERE` clause. Window functions are not allowed in `WHERE` — Postgres requires them in a subquery or CTE.
- **Implementation correct?** No.
- **Documentation correct?** Yes.
- **Recommendation**: Wrap the inner query in a subquery/CTE: `SELECT * FROM (SELECT …, row_number() over (…) AS row_rank FROM …) t WHERE (t.row_rank, t.instance_player_id) > (?, ?)`. The sort order is also wrong (the `orderBy` is on the inner query, not the outer); ensure the sort keys match the cursor's `(rank, instancePlayerId)` tuple. **Safe implementation fix** (the spec already documents cursor pagination; the bug is on the implementation side).

**8.2 — `rank` is emitted as a string (`"3"`) instead of a number**
- **Current behavior**: `data[*].rank = "3"` (string).
- **Documented behavior**: DTO declares `rank!: number`; the OpenAPI schema declares `type: 'number'`.
- **Root cause**: The Drizzle column alias `sql<number>\`row_number() over (...)\`.as('row_rank')` does not actually cast the PG return type. PG `bigint` (which `row_number()` returns) is serialized as a string by Drizzle / the PG client.
- **Implementation correct?** No.
- **Documentation correct?** Yes.
- **Recommendation**: Cast in SQL: `row_number() over (…)::int` (or `::text::int` after concat). Then `entry.rank` is a number in the mapper. **Breaking runtime behavior** for clients doing runtime type checks. The OpenAPI contract is already `number`, so SDKs are unaffected.

**8.3 — Cursor `rank` is a string (not a number)**
- **Current behavior**: Decoded cursor: `{ rank: "3", instancePlayerId: "…" }`.
- **Documented behavior**: DTO description: `Decoded payload: { rank: number, instancePlayerId: string }`.
- **Root cause**: Same as 8.2 — `JSON.stringify` serializes the string `"3"`.
- **Implementation correct?** No.
- **Documentation correct?** Yes.
- **Recommendation**: Same fix as 8.2. **Breaking client SDK** for any client that decodes cursors.

#### High findings

**8.4 — Leaderboard order is non-deterministic when all `scorePercent` are NULL**
- **Current behavior**: Three `joined` players with no attempts get ranks 1, 2, 3 in a non-deterministic order across requests.
- **Documented behavior**: Spec says "sorted by attempt score then by completion time".
- **Root cause**: `orderBy desc(scorePercent), timeTakenMs, instancePlayerId` — all three keys are NULL or tied. Postgres returns an implementation-defined order for ties.
- **Implementation correct?** No.
- **Documentation correct?** No (silent assumption that ties are stable).
- **Recommendation**: Add `joinedAt ASC` as a final tiebreaker in the `orderBy`. **Safe implementation fix**.

**8.5 *(High)* — Same `format: 'uuid'` issue** — same fix as 3.1.

**8.6 *(Medium)* — Same 404 example issue as 3.2** — same fix.

**8.7 *(Medium)* — `scorePercent` mapper uses `parseFloat` to coerce the PG `numeric` (returned as string) to a number**
- **Current behavior**: `mappers/instance-response.mapper.ts:74` does `parseFloat(entry.scorePercent)`.
- **Documented behavior**: DTO says `number`.
- **Root cause**: Drizzle's `numeric` type is returned as `string` by the PG client.
- **Implementation correct?** Yes (defensive workaround).
- **Documentation correct?** Yes.
- **Recommendation**: Either (a) cast the column to `double precision` in SQL, or (b) document this as a known mapper quirk. (a) is the cleanest fix.

**8.8 *(Info)* — The leaderboard endpoint does not list 500 in the spec; with the bug in 8.1 a 500 actually occurs. After 8.1 is fixed, the spec is consistent** ✓.

## 5. Cross-Cutting Findings

### X1. Path-parameter `format: 'uuid'` is missing on every `:id` endpoint (3, 4, 5, 6, 7, 8) — **High**

- **Spec**: `{ "name": "id", "required": true, "in": "path", "schema": { "type": "string" } }` (no `format`).
- **Standard**: `docs/standards/swagger.md:46` "UUIDv7 path parameters MUST set `format: 'uuid'` explicitly (this is enforced by `tag-openapi.spec.ts`)" and the `tag-openapi.spec.ts` regression test that "marks path id as uuid format".
- **Implementation**: uses `ParseUUIDPipe` (correct).
- **Resolution**: add a shared `ApiInstanceIdParam()` decorator in `transport/swagger/instance-swagger-decorators.ts` and apply to every handler with `:id`. **Safe documentation fix.**

### X2. Generic `ErrorResponseExamples` diverge from real module-specific `detail` — **Medium**

- **Endpoints affected**: 400/401/403/404 across all 8 endpoints.
- **Spec examples** (from `ErrorResponseExamples` in `src/common/swagger/swagger-schemas.ts`):
  - `notFound.detail = "The requested resource was not found"`
  - `forbidden.detail = "You do not have permission to perform this action"`
  - `unauthorized.detail = "Invalid or expired access token"`
  - `badRequest.detail = "Request validation failed"` (with `errors[]` array — but the actual response carries no `errors` array, just a joined `detail` string)
- **Real runtime details (instance module)**:
  - `INSTANCE_NOT_FOUND` → `"Quiz instance not found"`
  - `INSTANCE_NOT_HOST` → `"Only the host can perform this action"`
  - `GLOBAL_UNAUTHENTICATED` → `"Authorization header is missing"`
  - `GLOBAL_VALIDATION_FAILED` → joined class-validator messages, no `errors[]` array
- **Root cause**: the shared example constants are an abstraction that hides per-module `detail`. The instance module's local `instanceForbiddenResponse()` / `instanceNotFoundResponse()` / `instanceBadRequestResponse()` helpers all reuse the shared examples instead of providing module-specific ones.
- **Resolution**: replace shared example references with per-module constants in a new `transport/swagger/examples/error-examples.ts`. **Safe documentation fix.**

### X3. `PaginationMetaDto.nextCursor` schema is `type: 'object'` but the value is a string — **High**

- **Spec**: `PaginationMetaDto.nextCursor = { "type": "object" }`.
- **Runtime**: `nextCursor` is a base64url string (or `null`).
- **Per-endpoint `InstanceListPaginationDto` and `InstanceLeaderboardPaginationDto`**: correctly declared as `type: 'string'`.
- **Root cause**: the shared `PaginationMetaDto` in `swagger-schemas.ts:121-141` is wrong.
- **Resolution**: fix the shared `PaginationMetaDto.nextCursor` schema to `type: 'string', nullable: true`. Global change. **Safe documentation fix.**

### X4. `PaginationMetaDto.kind` declared but never enforced in the DTO — **Low**

- **Spec**: `kind` is a required discriminator string.
- **Runtime**: the presenter always emits `kind: 'cursor'`. There is no class-validator enforcing this.
- **Resolution**: not actionable; the kind is a fixed literal. **No change needed.**

### X5. `wrapPaginatedDto` in `instance.presenter.ts:23-37` does not call `normalizeTemporalFields` — **Critical** (see 2.2)

- **Runtime impact**: the list and leaderboard endpoints emit Postgres timestamp strings instead of ISO 8601.
- **The detail endpoint (`getInstanceByIdForController`) and the `joinInstance` / `startInstance` / `closeInstance` endpoints all use `ApiResponse.ok` which DOES normalize**, so the inconsistency is only on the paginated list/leaderboard paths.
- **Resolution**: in `wrapPaginatedDto`, replace `data: [...payload.items]` with `data: normalizeTemporalFields([...payload.items]) as T[]`.

### X6. `ListInstancesQueryDto` has no `@IsIn` / `@IsEnum` validators on `status` and `difficulty` — **Critical** (see 2.1)

- **Standard violation**: `docs/standards/validation.md:42` says "An enum field MUST declare `@IsEnum(EnumType)` and `@ApiProperty({ enum: EnumType })`."
- The `ListInstancesQueryDto.status` and `ListInstancesQueryDto.difficulty` fields are declared with `@ApiPropertyOptional({ enum: ... })` but no `@IsIn(…)` runtime validator.
- **Resolution**: add `@IsIn(INSTANCE_STATUSES)` and `@IsIn(QUIZ_DIFFICULTIES)` decorators.

### X7. `PlayerAlreadyJoinedError` is declared but never thrown — **High** (see 5.1)

- **Standard declared**: `problem-code-mapping.ts:949-963` has a comment "this exception is defined and exported but is currently NOT thrown by `instance.service.ts`".
- **Runtime impact**: the "duplicate join" path silently returns `INSTANCE_FULL` (wrong code/wrong message).
- **Resolution**: throw `PlayerAlreadyJoinedError` from `instance.service.ts:114` when the repository indicates a duplicate. **Breaking wire change** (status 400→409; `extensions.code` change). The class is already wired in `problem-code-mapping.ts` and the spec test (`instance-domain.errors.spec.ts`); only the throw site is missing.

### X8. `INSTANCE_NOT_HOST` 403 example uses the legacy generic message — **Medium** (see 6.3, 7.3)

- The shared `ErrorResponseExamples.forbidden.detail` is the legacy "You do not have permission to perform this action" which was rewritten in `problem-code-mapping.ts:880-882` to the specific "Only the host can perform this action" — but the example was not updated.
- **Resolution**: replace the example with one that matches the runtime `detail`. **Safe documentation fix.**

### X9. `nextCursor` for the list endpoint encodes a non-normalized timestamp — **High** (see 2.5)

- **Root cause**: the cursor encoding in `instance.service.ts:292-300` does `JSON.stringify({ createdAt: lastItem.createdAt, ... })` directly. The `createdAt` field at that point is the raw PG string.
- **Resolution**: normalize to `new Date(lastItem.createdAt).toISOString()` before encoding. **Breaking client SDK** for any client that decodes the cursor.

### X10. Cursor decoding is permissive — **Medium** (see 2.4)

- `instance.service.ts:270-274` does `JSON.parse(...) as InstanceCursorPayload` without validating the shape.
- For the leaderboard, the controller (`instance.controller.ts:349-350`) decodes the cursor at the controller level using `decodeBase64JsonCursor` which only catches JSON parse errors. A payload missing `rank` or `instancePlayerId` is silently ignored downstream.
- **Resolution**: add a tiny runtime type-check after decoding; on failure throw `BadRequestException('Invalid cursor')`.

### X11. No module-level OpenAPI spec test — **High**

- `docs/standards/swagger.md:74` requires "Each module MUST keep a module-level contract test under `src/modules/<module>/transport/` (e.g. `tag-openapi.spec.ts`)". The instance module does **not** have `instance-openapi.spec.ts`.
- **Impact**: none of the 8 endpoints' `format: 'uuid'` requirement, query enum validation, or example completeness is regression-protected.
- **Resolution**: add `src/modules/instance/transport/instance-openapi.spec.ts` modeled after the tag variant. **Safe documentation/test fix.**

### X12. No DTO-level `*.spec.ts` for `instance.dto.ts` — **Medium**

- The standard says: "DTO validation contracts (`@IsOptional`, `@Min`, `@Max`, `@Type(() => Number)`) are locked by co-located unit specs (see `tag-ranking-query.dto.spec.ts`)." There is no `instance.dto.spec.ts`.
- **Impact**: no regression test for the missing `@IsIn` validators on `status`/`difficulty` or for the `2 ≤ maxPlayers ≤ 100` range.
- **Resolution**: add `src/modules/instance/dto/request/instance.dto.spec.ts`.

### X13. `displayName`, `avatarUrl`, `hostDisplayName` are always `null` for the seeded users — **Info**

- The seed has no profile data for the seeded users. The field is correctly nullable in the DTO.
- **Resolution**: none. The contract is correct.

### X14. `INSTANCE_NOT_HOST` does not include the host's userId in the response — **Low**

- The 403 response has no machine-readable identifier of the actual host. The error is human-only.
- This is consistent with the rest of the project, so **no fix needed**.

## 12. Prioritization & Migration Plan

The findings are organized into **5 implementation phases** that minimize risk, reduce merge conflicts, and preserve API stability as much as possible. Each phase is independent where possible.

### Phase 1 — Critical runtime correctness (no wire-shape change required)

**Goal**: Eliminate the 500-level runtime errors caused by invalid SQL and missing validators. Make the wire behavior match what the OpenAPI document already claims.

**Issues included**:
- **2.1** (Critical) — Add `@IsIn(INSTANCE_STATUSES)` and `@IsIn(QUIZ_DIFFICULTIES)` to `ListInstancesQueryDto`. (Documentation is already correct; this is a runtime fix to match the spec.)
- **8.1** (Critical) — Fix `row_rank` in `WHERE` clause by wrapping the inner query in a CTE/subquery.
- **8.2** (Critical) — Cast `row_number() over (...)` to `::int` so `rank` is a number on the wire.
- **8.3** (Critical) — Implicit fix from 8.2 (cursor rank becomes a number).
- **1.1** (Critical) — Translate `23503` FK violation on `quizVersionId` into a 400/404 (preferably 404 with a new `QUIZ_VERSION_NOT_FOUND` code).

**Reason these belong together**: each of these causes a **500 on real user traffic** (invalid filters, missing FK, cursor pagination). All other improvements are moot while the server is throwing 500s on documented behavior.

**Dependencies**: none.

**Estimated implementation complexity**: Medium.
**Estimated implementation risk**: Low.

**Migration safety**:
- 2.1, 8.1, 8.2, 8.3: **Safe implementation fixes.** The OpenAPI spec already documents the correct behavior; the runtime was the side that was non-conforming.
- 1.1: **Breaking API contract** (status code change for the FK-violation case). **Requires product decision** (400 vs. 404). Add a deprecation log on the 500 path for one release.

**Public API contract change**: only 1.1 (and only for the FK-violation case). Frontend clients that handle the success case won't notice; clients that parse `detail` strings for the FK case will need to update.

**Generated SDK impact**: OpenAPI 500 removal.

**Database migrations required**: no.

**Existing tests**: update `quiz-instance.repository.spec.ts` (if any) for the CTE shape.

**New tests required**:
- `instance-openapi.spec.ts` asserting `format: 'uuid'` on `:id`.
- A controller e2e for the `?status=invalid` case.
- A repository unit test for the leaderboard CTE.
- A controller e2e for the missing-`quizVersionId` case.

---

### Phase 2 — Wire-shape / runtime correctness (breaking for one path)

**Goal**: Distinguish the duplicate-join case from the capacity-full case; clean up timestamp serialization on list endpoints; add cursor shape validation.

**Issues included**:
- **2.2** (Critical) — Add `normalizeTemporalFields` to `wrapPaginatedDto`.
- **2.5** (High) — Normalize the `createdAt` encoded into the list `nextCursor` to ISO 8601.
- **2.4** (High) — Validate the decoded cursor's shape in `instance.service.ts:268-274` (list).
- **2.4-leaderboard** (High) — Same for the leaderboard cursor in `instance.controller.ts:349-350`.
- **5.1** (Critical) — Throw `PlayerAlreadyJoinedError` (status 409, code `PLAYER_ALREADY_JOINED`) on duplicate join.
- **8.4** (High) — Add `joinedAt ASC` as a stable tiebreaker in the leaderboard query.

**Why this phase before Phase 3**: these are wire-shape changes that should land before any client-visible documentation updates.

**Dependencies on previous phases**: Phase 1 (2.2 needs the `createdAt` to be normalized; 5.1 depends on the joinInstanceAtomic discriminator).

**Estimated implementation complexity**: Medium.
**Estimated implementation risk**: Medium (5.1 is a **Breaking** change for the duplicate-join case).

**Migration safety**:
- 2.2, 2.4, 8.4: **Safe implementation fixes** (matches documented behavior).

**Goal**: Differentiate `closed` and `finished` from `running` in the start/close flows.

## 16. Notes on Scope

- **WebSocket gateway** (`src/modules/instance/transport/gateway/instance.gateway.ts`) is out of scope for this REST contract audit. The gateway uses `WsExceptionFilter` (`ws-exception.filter.ts`) which only handles `UnauthorizedException` and generic errors — domain errors thrown from the gateway path will hit the generic branch and emit `{ code: 'INTERNAL_ERROR', message: 'An unexpected error occurred' }`. This is a deliberate design choice (documented in `instance.module.ts:60-62`) and is consistent with the rest of the project's WS modules.
- **Domain-event emission** (e.g. `PlayerJoinedEvent`, `InstanceStartedEvent`, `InstanceClosedEvent`) is not part of the REST contract; the WebSocket push is out of scope.
- **Notification fan-out** (host-notification on join/disconnect) is not part of the REST contract; the application service calls the notification port via `void this.notifyHostPlayerJoined(...)` (`instance.service.ts:134-139`).
