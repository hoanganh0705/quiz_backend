# Migration Standard

> Project-specific rules for API evolution, schema migrations, deprecation, and rollout.
> Operational conventions for `db:migrate` and CLI tools are documented in the codebase and called out here where relevant. Out of scope: infrastructure migration (no IaC files in this repo).

## Purpose

Defines how API contracts and database schema changes move through the system without breaking existing clients. Every change MUST follow the lifecycle described here.

## Scope

Applies to schema migrations under `src/core/database/migrations/`, DTO/endpoint evolution documented in `src/modules/<m>/dto/` and `src/modules/<m>/transport/`, and CLI tooling in `src/commands/`.

## Source of Truth

- `drizzle.config.ts` — schema and migration output paths.
- `package.json` — `db:generate`, `db:migrate`, `db:studio`, `db:seed`, `generate:openapi`, `test:e2e`.
- `src/core/database/migrations/0000_*.sql` — existing migration patterns.
- `src/commands/outbox.ts` — production safety for operational tooling.
- `src/common/audit/audit-log.service.ts` — auditable change records.
- `PROJECT_CONSTITUTION.md` §2.3 (Backward compatibility principle).

## Rules

### API compatibility

- Every change MUST be additive. New fields, new endpoints, new optional query parameters are allowed.
- MUST NOT remove, rename, or change the type of any existing field on a response DTO without going through the deprecation lifecycle below.
- MUST NOT change a path parameter's format (UUID → slug, or vice versa) without supporting both shapes during a deprecation window.
- MUST NOT alter cursor encoding semantics. A new cursor encoding is a major version.
- A change in HTTP status for an existing endpoint (e.g. `200 → 204`) is a breaking change and MUST go through the deprecation lifecycle.

### Database schema migrations

- Schema changes MUST be generated by `pnpm db:generate`. Manual edits to a generated migration are allowed only when the generator cannot express the change; the PR MUST contain a comment explaining the deviation.
- Migration files MUST NOT be deleted after they are merged. Compaction requires a separate "DB rebuild" runbook, not deletion.
- A migration that drops a column or table MUST include the backfill / archival story in the same PR description.
- A migration that introduces a `NOT NULL` column without a default MUST be paired with a backfill migration that runs before the constraint is enforced.
- A migration that creates or alters an index on a populated table MUST be reviewed for lock impact (PostgreSQL `CREATE INDEX CONCURRENTLY` is preferred for production; Drizzle's default is non-concurrent and is acceptable only in dev).
- Schema files (`core/database/schema/`) MUST be updated in the same PR as the migration they introduce.

### Endpoints

- New endpoints MUST have updated examples and a module-level OpenAPI test added in the same PR.
- A mutation endpoint MUST be idempotent or MUST require a unique idempotency key when retried. The current codebase does not enforce this; future additions MUST land alongside an `Idempotency-Key` header rule in `api.md` and `validation.md`.

### Deprecation lifecycle (response shapes)

- Phase 1 — Mark as deprecated:
  - Add `@deprecated` JSDoc to the response DTO field and an `x-quiz-deprecated-reason` extension in the corresponding Swagger field (the convention here is JSDoc `@deprecated` plus a comment in the changelog).
  - Update the contract test to acknowledge deprecated fields (`tag-openapi.spec.ts` pattern).
  - Add a `DeprecatedAt`/`SunsetAt` ADR if the field or endpoint is removed in a future version.
- Phase 2 — Communicate:
  - Document the deprecation in the generated OpenAPI's `description` and in any changelog file under `docs/`.
  - Add structured logging on inbound requests to count usage (the codebase already has `PinoLogger`; this is operational and not part of the test gate).
- Phase 3 — Remove:
  - Removal requires the deprecation window to have elapsed (default 90 days unless a longer compliance need exists).
  - Removal MUST happen in a major version commit (URL prefix bump — see `api.md`).
  - Removal MUST be accompanied by an updated test (asserts absence) in the e2e suite.

### Operational tooling

- A CLI tool that performs a destructive write MUST refuse to run in production by default and require the `ALLOW_PROD_<TOOL>_OPERATIONS=true` env flag. Reference: `src/commands/outbox.ts`.
- A new CLI MUST follow the same pattern. The CLI MUST log its name, the actor (caller identity), the timestamp, and the affected IDs in its audit output.
- Outbox event lifecycles (`inspect`, `retry`, `discard`) are referenced from the outbox CLI and are required to be auditable.

### Seed and ad-hoc data

- The seed script (`db:seed`) MUST run in dev only. Production MUST NOT seed by default; the production runbook for any seed is a manual CLI invocation guarded as above.
- Migrations MUST NEVER seed data. Seeding happens only via `db:seed`.

### Rollout

- A migration that takes non-trivial lock time MUST land behind a feature flag OR run via `db:migrate` during a maintenance window, both with `pnpm db:generate` artifacts committed in the same PR.
- A change to error codes MUST be staged: new codes are added, old codes are kept alive for the deprecation lifecycle.
- A change to a path or query parameter MUST be staged: the old parameter is accepted and ignored in the same release, then removed only after the deprecation window.

### API and breaking-change boundaries

- A breaking change MUST be made under a new URL prefix (`api/v2/`) and the prior prefix MUST stay live until the deprecation window elapses.
- The project's `GENERATE_OPENAPI` MUST be committed alongside any prefix change so the deployed artifact matches the documented path.

### Compatibility tests

- A change to the API surface MUST update `tag-openapi.spec.ts` (or the module's analog) to keep schema-level assertions accurate.
- A change that introduces a new error code MUST add a case to `test/rfc7807.e2e-spec.ts`.

## Examples

### Phase 1 deprecation of a response field

```typescript
// before
@ApiProperty()
rating: number;

// after
@ApiProperty({ description: '@deprecated Use weightedRating instead. Removed in v2.' })
/** @deprecated since 2026-04-01; sunset 2026-07-01 — use weightedRating. */
rating: number;
```

### Migration with backfill

```sql
-- 0001_add_weighted_rating.sql
ALTER TABLE quizzes ADD COLUMN weighted_rating numeric;
UPDATE quizzes SET weighted_rating = rating * 0.5;
ALTER TABLE quizzes ALTER COLUMN weighted_rating SET NOT NULL;
```

### Production-safe CLI

```bash
# refused in production by default
pnpm ts-node src/commands/outbox.ts discard --id <id>
ALLOW_PROD_OUTBOX_OPERATIONS=true pnpm ts-node src/commands/outbox.ts discard --id <id>
```

## Non-goals

- Documenting infrastructure-as-code (Terraform, Helm) — not present in the repo.
- Documenting feature flag service configuration — referenced as a flag, not as a server in this codebase.
- Documenting multi-region deploy or canary deploys — not present in the repo.

## Future considerations

- A canonical ADR / RUNBOOK directory under `docs/` should be created if long-lived migration notes proliferate. The default location is `docs/migrations/<name>.md` (this directory currently holds historical / context material and is acceptable as the deprecation register too).
- A version strategy beyond URL prefix (e.g. header-based) is not implemented and MUST NOT be invented without first updating `api.md` and this standard in the same change.
